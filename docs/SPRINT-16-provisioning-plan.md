## Contexto

Hoy crear un cliente en Prompt Studio solo inserta la fila `clients` y siembra
la v1.0. Los dos pasos que el equipo hace a mano justo después son siempre los
mismos: duplicar el flujo de n8n y renombrarlo `IA Mensajes {Cliente}`, y crear
la tabla `chats_{Cliente}` en el proyecto Supabase "chats". Este sprint mueve
esos dos pasos al modal de Nuevo cliente, con reintento desde la ficha si algo
falla.

Resultado esperado: crear "Acalai" deja listo el flujo `IA Mensajes Acalai`
(inactivo, ya vinculado para el sync de prompts) y la tabla `chats_Acalai`
conectada al panel de Historial de conversaciones.

## Decisiones tomadas

1. Plantilla n8n: default configurado en Settings, sobrescribible en el modal.
2. Nombre de tabla: sin acentos, sin espacios ni signos, conservando mayúsculas.
   "Bad Boys Toys" produce `chats_BadBoysToys`.
3. Creación de la tabla: Management API de Supabase con `SUPABASE_ACCESS_TOKEN`.
4. El cliente se crea siempre. Cada paso reporta su resultado y se reintenta
   desde la ficha.
5. El flujo duplicado se auto vincula (binding api, sync activo).
6. El flujo nace inactivo en n8n.
7. Ambas acciones son checkboxes marcados por default en el modal.

## Dos claves de diseño

**Un endpoint aparte, no dentro de `POST /api/clients`.** El aprovisionamiento
vive en `POST /api/clients/[id]/provision`, que el modal llama después de crear
y que los botones de reintento vuelven a llamar. Así la regla "el cliente se
crea siempre" es estructural y no depende de un try/catch, y no hay lógica
duplicada entre creación y reintento.

**Idempotencia por nombre, sin columnas de estado.** Nada de una columna
`provisioning` en `clients`: los dos pasos son idempotentes y el estado se
deriva de la realidad.

- n8n: antes de duplicar se busca en `listWorkflows()` un flujo llamado
  `IA Mensajes {Cliente}`. Si ya existe, se adopta y solo se crea el binding.
  Esto evita el caso feo de reintentar y quedarse con dos flujos duplicados.
- chats: `create table if not exists` y, si la tabla ya aparece en
  `listChatsTables()`, se adopta y solo se guarda `clients.chats_table`.

La ficha deriva qué ofrecer: sin binding api, botón de duplicar; con
`chats_table` en null, botón de crear tabla. Un paso que falló se reporta en el
momento (modal) y su rastro es simplemente que el botón sigue ahí.

## Riesgos aceptados

- `SUPABASE_ACCESS_TOKEN` es un token de cuenta completa. Mitigación en código:
  el ref del proyecto sale de env (`CHATS_SUPABASE_PROJECT_REF`), el DDL se arma
  con una plantilla fija en el servidor y el nombre de tabla pasa por
  `CHATS_TABLE_RE`. Nunca viaja SQL que venga del navegador. Si más adelante el
  alcance del token incomoda, el reemplazo es una función `security definer` en
  el proyecto chats (como `supabase/chats/001_list_chat_tables.sql`) y solo
  cambiaría `lib/chats-admin.ts`.
- El flujo duplicado hereda credenciales y `webhookId` de la plantilla. Por eso
  nace inactivo: se revisa y se prende a mano. Ver el punto 3 de verificación.

Nuevo `lib/chats-table-name.ts`, módulo puro sin imports de Supabase (lo usa


NFD, quitar diacríticos, `replace(/[^A-Za-z0-9]/g, "")`, prefijo `chats_`. No
tocar el `normalize()` privado de `lib/db/chats-history.ts:89`: ese baja a
minúsculas porque compara, no nombra.

DDL emitido (idéntico a las tablas existentes, verificado en el proyecto chats;
identificador entre comillas porque lleva mayúsculas):

```sql
create table if not exists public."chats_X" (
  id bigint generated by default as identity primary key,
  created_at timestamptz not null default now(),
  numero_de_mensajes numeric,
  id_de_kommo text,
  historial text
);
alter table public."chats_X" enable row level security;
notify pgrst, 'reload schema';
```

Sin `grant` explícito: las tablas actuales tienen los privilegios default de
Supabase (anon, authenticated, service_role) que se heredan al crear en `public`
como `postgres`. El `notify pgrst` es para que PostgREST vea la tabla al
instante y el panel de historial no dé 404.

Tests en `lib/chats-table-name.test.ts` con `node:test`, como
`lib/format.test.ts`: espacios, acentos, apóstrofes, nombre que empieza con
dígito, nombre solo de símbolos, y que `buildCreateChatsTableSql("chats_X; drop
table y")` lance.

### S16-T5: orquestador y endpoint de aprovisionamiento (medio)

Nuevo `lib/provisioning.ts`:

```ts
export type ProvisionOptions = {
  duplicateWorkflow: boolean;
  template?: { connectionId: string; workflowId: string };  // override del default
  createChatsTable: boolean;
};
export type StepResult = { ok: true; detail: string } | { ok: false; error: string };
export async function provisionClient(clientId: string, opts: ProvisionOptions):
  Promise<{ workflow: StepResult | null; chats: StepResult | null }>
```

Cada paso en su propio try/catch: un fallo se reporta, nunca se propaga.

`duplicateAndBind`: `getConnectionCreds` (`lib/db/n8n-connections.ts:138`) ->
`listWorkflows` buscando `IA Mensajes {cliente}` (si existe, se adopta) ->
si no, `getWorkflow(plantilla)` + `createWorkflow` con el nombre nuevo ->
`listAgentNodes` (`lib/n8n/agent-node.ts:142`) sobre el flujo resultante ->
con exactamente un nodo AI Agent, `readSystemMessage(node)` para saber el
`expression_prefix` y `createApiBinding` (`lib/db/n8n-bindings.ts:80`).
Con cero o varios nodos: el flujo queda creado y el resultado dice "el flujo se
duplicó, tiene N nodos AI Agent, vincúlalo a mano". Misma ética que
`matchChatsTable` y `locateBoundAgent`: no adivinar.

`ensureChatsTable`: `chatsTableName(client.name)` -> `listChatsTables()`; si ya
está, adoptarla; si no, `createChatsTable(name)` -> `updateClient(id, {
chats_table: name })`. Ojo con el orden actual: `createClient` llama
`suggestChatsTable` ANTES del insert (`lib/db/clients.ts:220`), así que en un
cliente recién creado `chats_table` siempre viene en null y este paso es el que
lo llena.

Nueva ruta `app/api/clients/[id]/provision/route.ts`: valida con un
`provisionClientSchema` nuevo en `lib/schemas/clients.ts`, resuelve la plantilla
(override si viene, si no la de la conexión) y responde 200 con los dos
`StepResult` aunque alguno haya fallado. Si no hay plantilla configurada, el
paso de n8n responde `ok: false` con "No hay plantilla configurada en Ajustes".

`app/api/clients/route.ts`, `ImportModal` y el finalize del Creator no se tocan.

## Ajuste posterior (28 jul 2026)

La primera corrida real desmintió el supuesto del punto 3 de Verificación: la
plantilla no tiene un solo nodo AI Agent, tiene tres (Router,
dudas/conversacion, AI Agent de calendario). El cliente se creó bien y la tabla
también, pero el paso de n8n terminó en "tiene 3 nodos AI Agent. Vincúlalo a
mano desde la ficha", o sea que el caso que T5 trataba como excepción es el
caso normal.

Dos cambios, ya en `main` vía `sprint-16/node-pick-and-version-sync`:

- **Elegir el nodo en vez de fallar.** Con más de un agente, el `StepResult`
  fallido de `lib/provisioning.ts` lleva `pick` con la conexión y el id de la
  copia. `NewClientModal` cambia "Continuar" por "Elegir nodo" y navega a
  `/library/{id}?bind=1&conn=…&wf=…`; `N8nDeploymentCard` lee esos params y
  abre `N8nBindingModal` con `preselect`, ya posado en el flujo duplicado. El
  botón de reintento hace lo mismo sin pasar por la URL. Con cero agentes no
  hay nada que elegir y sigue siendo error seco.
  Se descartó guardar el nodo por defecto junto a la plantilla en Ajustes
  (`template_node_name` en la conexión): ahorra un clic por cliente pero pide
  migración y se rompe callado si la plantilla renombra el nodo. Si el clic
  molesta, esa es la mejora.
- **Sincronizar sin promover.** Un flujo recién vinculado no tenía forma de
  recibir el prompt que el cliente ya tenía: el push colgaba de promover una
  versión, y el link "Ver diff / sincronizar" de la tarjeta solo aparecía con
  drift, nunca en `no_baseline`. `/api/clients/{id}/n8n-sync` ya aceptaba
  cualquier `version_id`, así que solo faltaba el disparador: botón
  "Sincronizar con n8n" en la vista de cualquier versión, y el link de la
  tarjeta visible siempre que haya versión de producción.

Queda pendiente el resto de la verificación end to end (puntos 4 a 7).
